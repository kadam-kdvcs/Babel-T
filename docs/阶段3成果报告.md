## 一、阶段三目标

在阶段一（本地切分/扫描/占位）和阶段二（阿里云机器翻译双模式）基础上，把系统从“纯机械化流程”升级为“机器翻译 + LLM 辅助审校”的完整工作流。

阶段三共经历三次迭代：

| 子阶段 | 核心目标 |
|---|---|
| 阶段 3.0 | 接入 DeepSeek / OpenAI 兼容接口，生成 **8 项结构审校报告** |
| 阶段 3.1 | LLM 额外输出 **逐段纠正后译文**，页面支持两种翻译展示 |
| 阶段 3.2 | LLM 执行 **直接翻译 → 修正 → 最终仲裁** 三轮处理，页面固定展示 **四结果对比** |

## 二、技术方案

### 1. 配置集中管理

- 所有翻译与 LLM 配置集中在 `modules/settings.py`
- 环境变量使用 `.env`，密钥绝不进入代码和仓库
- 翻译与审校均支持 `mock` / `api` 双模式
- api 缺密钥时自动回退占位并在页面黄色提示

### 2. LLM 调用

- 使用 `requests` 直调 DeepSeek / OpenAI 兼容接口
- 不引入 openai SDK、LangChain 等额外依赖
- `DEEPSEEK_API_URL` 为 base URL，自动拼接 `/chat/completions`
- temperature 固定 0.3
- 异常体系：
  - `ReviewError` 基类
  - `ReviewNetworkError` / `ReviewBusinessError` / `ReviewParseError`

### 3. 提示词模板

文件：`prompts/` 目录下三份独立模板

- `direct_translation_prompt.md`：只负责直接翻译，上下文不提供 API 译文
- `correct_translation_prompt.md`：只负责修正，上下文提供原文 + API 译文
- `review_report_prompt.md`：最终仲裁，上下文提供原文 + 直接翻译 + 修正结果，不提供 API 译文

当前阶段三（3.2）采用**三次独立调用**，各阶段输出：

```text
直接翻译阶段：
## 直接翻译结果
第1段：...
第2段：...

修正阶段：
## API译文修正结果
第1段：...
第2段：...

最终仲裁阶段：
## 最终结果
第1段：...
第2段：...

## 翻译取舍说明
说明选择了哪个版本及原因

## 审校报告
### 1. 文本概况
### 2. 术语命中与风险
...
```

### 4. 多结果解析与回退

`reviewer.generate_review_bundle` 返回：

```python
{
    "report": str,
    "direct_translations": list[str],
    "corrected_translations": list[str],
    "final_translations": list[str],
    "tradeoff_notes": str,
}
```

若 LLM 未按新版结构输出，安全回退：

- `direct_translations` / `corrected_translations` → 原始 API 译文
- `final_translations` → 优先回退 `corrected_translations`
- `tradeoff_notes` → 占位提示“模型未输出取舍说明，请人工复核”
- `report` → 保留整段返回文本

### 5. 翻译性能优化

- 原 `translate_paragraphs`：串行兼容入口
- 新增 `translate_paragraphs_parallel`：
  - `ThreadPoolExecutor(max_workers=4)`
  - API 多段翻译并发请求
  - 每段完成回调 `on_translation(index, translation)`
  - 任一段失败取消未开始请求并抛出带段落号的异常

### 6. 动态渲染

- 新增 `run_pipeline_progressive`
- 页面流程：
  1. 点击后立即显示每段阿语原文
  2. 每段译文位置显示“等待翻译…”
  3. 某段 API 翻译完成 → 原文下方立即显示译文
  4. 全部翻译完成 → 提示“正在请求 LLM 纠正与审校…”
  5. LLM 返回 → 渲染完整四结果对比与审校报告

## 三、页面功能

### 当前页面（阶段 3.2）

- 输入：阿语原文粘贴框，预填示例文本
- 主按钮：开始翻译与审校
- 结果区：
  1. **四结果对比**
     - 原始 API 译文
     - LLM 直接翻译结果
     - LLM 修正结果
     - LLM 最终结果（以原文为准）
  2. 术语命中表
  3. 专名命中表
  4. 审校报告
- 最终仲裁原则：以原文为最高依据，不添加原文未有的信息

### 历史版本功能回顾

#### 阶段 3.0

- 8 项审校报告结构：
  1. 文本概况
  2. 术语命中与风险
  3. 专名命中与统一性
  4. 重点风险句段
  5. 语体与领域适配
  6. 文化/政治语境提醒
  7. 总体结论
  8. 人工复核建议

#### 阶段 3.1

- LLM 增加“纠正后译文”
- 页面提供两种展示视图：
  - 仅显示 LLM 纠正后译文
  - 原始 API 译文 + LLM 纠正后译文
- 后来在阶段 3.2 被四结果对比取代

## 四、安全与健壮性

- API Key 只存在于本地 `.env`
- 异常消息全部为中文，且不包含密钥
- 业务错误响应片段截断 200 字符
- 用户输入先 `html.escape` 再渲染，防止 XSS
- LLM 报告渲染使用 `st.markdown` 且不传 `unsafe_allow_html`
- api 缺密钥自动回退占位，不崩溃
- LLM 调用失败保留上次成功结果
- 模型输出未按结构返回时安全回退，不导致页面崩溃
- **降级明确标注**：若 LLM 解析失败回退到 API 译文/修正结果，页面明确标注“已降级到 API 译文/修正结果”，不会伪装成 LLM 成功结果
- **代码拆分**：流水线在 `pipeline.py`，Streamlit 渲染在 `streamlit_ui.py`，LLM 解析在 `modules/reviewer_parsing.py`，降低 app.py / reviewer.py 单体体积
